# Polvo CLI & Reasoning-Aware Configuration Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Implement a modern, simple CLI (`polvo`) for managing the Polvo Model Router, including a guided setup flow for providers and tiers, and support for provider-specific parameters (e.g., reasoning effort).

**Architecture:** 
1. **CLI Layer**: A Python-based CLI (using `typer` or `argparse`) that interacts with the system and the config file.
2. **Config Layer**: A YAML-based configuration stored in `~/.config/polvo/config.yml`.
3. **Service Layer**: The CLI wraps existing `polvoctl.sh` commands for lifecycle management.
4. **Backend Layer**: The proxy merges tier-specific `extra_params` into the upstream API calls.

**Tech Stack:** Python 3.11, PyYAML, `typer` (suggested for CLI), `polvoctl.sh`.

## Task 1: Backend support for `extra_params`

**Objective:** Allow tiers to hold arbitrary parameters (like `reasoning_effort` or `budget_tokens`) and merge them into upstream requests.

**Files:**
- Modify: `src/model_router/models.py`
- Modify: `src/model_router/proxy.py`

**Step 1: Update `ModelSpec`**
Add `extra_params: dict[str, Any] = field(default_factory=dict)` to the `ModelSpec` dataclass.

**Step 2: Update Proxy Request Body**
In `src/model_router/proxy.py` inside `_process_chat`, merge the `extra_params` of the routed tier into the `upstream_body`:
```python
upstream_body = dict(body)
upstream_body.update(routed_spec.extra_params) # Merge reasoning/sampling params
upstream_body["model"] = routed_model
```

**Step 3: Verification**
Add a test in `tests/test_proxy.py` ensuring that a tier with `extra_params` has those params present in the `fake_post` request body.

**Step 4: Commit**
`git commit -m "feat: add extra_params support for provider-specific settings"`

## Task 4: Interactive Setup Flow (`polvo setup`)

**Objective:** Implement a guided interactive process to configure the router from scratch.

**Files:**
- Modify: `src/polvo_cli/main.py`
- Create: `src/polvo_cli/setup.py` (setup logic)

**Step 1: Provider Configuration**
- Prompt for Provider Name (e.g., "OpenAI", "Anthropic").
- Prompt for `base_url`.
- Prompt for `api_key`.

**Step 2: Tier Configuration (The "Omakase" vs Custom flow)**
- Display a brief English explanation of the 4 roles:
  - `mini`: trivial/mechanical tasks.
  - `air`: standard implementation.
  - `pro`: high-cognitive/unclear path.
  - `ultra`: systemic synthesis/hardest problems.
- Ask: `"Use Polvo Omakase (recommended defaults) or Custom Names?"`
- If Custom: Prompt for the display name of each tier.
- For each tier: Prompt for the `model` ID.

**Step 3: Reasoning Levels Configuration**
- Ask: `"Would you like to configure reasoning levels (extra_params) for any tier?"`
- If yes: allow adding key-value pairs (e.g., `reasoning_effort: high`) to specific tiers.

**Step 4: Save Config**
Write the resulting configuration to `~/.config/polvo/config.yml`.

**Step 5: Verification**
Run `polvo setup`, complete the flow, and verify that `~/.config/polvo/config.yml` contains the expected YAML.

**Step 6: Commit**
`git commit -m "feat: implement interactive polvo setup flow"`

## Risks & Tradeoffs

- **CLI Dependency**: Adding `typer` adds a dependency. If the user wants zero-dependency, we'd use `argparse`, but `typer` is significantly better for interactive flows.
- **Config Format**: YAML is easy for humans but can be corrupted by manual edits. The CLI should validate the YAML on load.
- **Service State**: The CLI assumes `polvoctl.sh` is present in the repo root. If the CLI is installed globally, it must find the `polvoctl.sh` relative to the installation path or via a config entry.
